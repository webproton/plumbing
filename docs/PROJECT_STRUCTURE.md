# PlumbingProject — структура и устройство проекта

Живой документ: описывает, **что есть**, **как работает** и **что менялось**.
Дополняется после каждого шага из [ROADMAP.md](ROADMAP.md). Пофайловая карта, удалённое и архив —
в [PROJECT_MAP.md](PROJECT_MAP.md).

## 1. Обзор

Интернет-магазин сантехники (B2C/B2B) со складским учётом, приёмкой товара по накладным
поставщиков (Excel/XML) и сканером штрихкодов.

| Слой | Технологии |
|---|---|
| Backend | Python 3.12, Django 5.2 LTS, DRF 3.18, SimpleJWT 5.5, allauth 65 + dj-rest-auth 7 |
| БД / кэш / очередь | PostgreSQL 14, Redis (кэш Django; очередь Celery — отдельная БД Redis) |
| Фоновые задачи | Celery 5 (`worker` + `beat`) |
| Парсеры | openpyxl, pandas, rapidfuzz |
| Frontend | React Router 8 (SSR), React 19, TypeScript, Tailwind CSS 4 — `frontend/web` |
| Infra | Docker Compose, nginx, gunicorn |

## 3. Backend: приложения и ответственность

### Витрина (`frontend/web`)
SSR на React Router 8: страницы рендерятся на сервере и гидрируются в браузере (поисковики видят готовый HTML,
JSON-LD и OG-теги товара). Все обращения к Django — из `loader`/`action` на сервере витрины. JWT пользователя
хранятся в подписанной HttpOnly-cookie сессии витрины (схема BFF): JavaScript в браузере токенов не видит,
истёкший токен обновляется автоматически. Корзина гостя — по `cart_uuid` в сессии, после входа переходит к
пользователю (`GET /api/orders/cart/current/`). Формы работают и без JavaScript. Старые адреса SPA
(`/products/…`) отвечают 301 на новые (`/product/…`, `/catalog`).

### accounts
- `User` (логин по email), `Profile` (контакты, создаётся сигналом при создании пользователя;
  для анонимных заказов создаётся профиль без пользователя).
- Эндпоинты `/api/dj-rest-auth/`: `login/`, `logout/`, `user/`, `profile/`, `password/*`,
  `token/refresh/`, `registration/`.
- Вход разрешён только с подтверждённым email (`ACCOUNT_EMAIL_VERIFICATION=mandatory`).

### products
- `Category` → `Product` → `ProductVariant` (цена, скидка, штрихкод, код, остаток `stock`/`reserved`,
  себестоимость `cost_price`, ~20 атрибутов мебели/сантехники). `available=False` — вариант скрыт из каталога.
- `ProductVariant.save()` генерирует slug, код, штрихкод и картинку штрихкода, пересчитывает скидку.
- **Каталог показывает только товары, у которых есть видимый вариант**; цена в списке — минимальная среди
  видимых вариантов («от …»); в карточке — только видимые варианты, у каждого `in_stock` и `available_qty`.
- Сортировка `?ordering=price|-price|name|-name|new` (другие значения игнорируются), поиск `?search=` — по
  названию, артикулу и штрихкоду. Число SQL-запросов не зависит от количества товаров на странице.
- Эндпоинты: `/api/products/`, `/api/category/`, `/api/new_products/`, `/api/wishlist/`.

### orders
**Кабинет (`/api/orders/manage/`, `orders/manage.py`).** Администратор ведёт все заказы; продавец видит заказы со
своими товарами и меняет только те, где все позиции его (иначе смена статуса списала бы чужой товар). Действия:
`status/` (разрешённые переходы `in_processing → delivering → delivered → completed`, отмена до списания; склад
меняет `services.change_status`), `payment/`, `note/` (заметка менеджера), `assign/`, `counts/` (по статусам).
Подписи статусов переводятся (`gettext_lazy` в `Order.STATUS` и др.) — API отдаёт их на языке запроса.

Модели: `Cart` (анонимная по `cart_uuid` или пользователя) → `CartItems`; `Order` → `OrderItem`
(снимок названия, артикула, цены и количества на момент оформления); `Order.stock_state` —
`none` (старые заказы) / `reserved` / `written_off` / `released`.

**Сервис `orders/services.py`:**
- `create_order_from_cart` — блокирует корзину (двойной клик не создаст второй заказ), фиксирует позиции
  и цены, **резервирует товар** (всё или ничего; при нехватке — `400 insufficient_stock`), уведомления
  отправляются после коммита;
- `change_status` — единая точка смены статуса (API отмены и Django admin):
  `canceled` → снять резерв; `delivered`/`completed` → списать со склада (`write_off_reserved`);
  отменить уже списанный заказ нельзя (нужен возврат);
- `cancel_by_customer` — клиент может отменить только свой заказ «в обработке» и до оплаты.

**Корзина:** `POST /api/orders/cart/` — «заменить содержимое» (клиент присылает корзину целиком; раньше
количества прибавлялись и росли при каждой синхронизации); `PUT/PATCH /cart/{id}/` — установить количества
(0 — удалить); позиция обязана иметь вариант (если у товара один вариант — подставляется сам);
в ответе по каждой позиции `price` выбранного варианта и `available` (доступно к заказу).

**Заказ:** `POST /api/orders/order-create/` — только по `cart_uuid` (поле `cart` с числовым id удалено —
по нему можно было оформить чужую корзину). Имя: буквы, пробел, дефис, апостроф. Телефон нормализуется к
`+380…`. История `GET /api/orders/history/` — только для авторизованных.

**Уведомления** (`orders/notifications.py`, `app/core/telegram.py`): сообщение менеджеру о новом заказе в Telegram,
таймаут 5 с, экранирование HTML, round-robin менеджеров через счётчик в Redis.

**Письма покупателю** (`orders/customer_notifications.py`): на языке оформления (`Order.language` — из
Accept-Language витрины), текст + HTML, ответ на письмо — на email магазина. События и где возникают:

| Событие | Когда | Ключ (один раз на заказ) |
|---|---|---|
| `created` | заказ оформлен | `created` |
| `shipped` | статус «Доставляется» (вручную или сам при вводе/создании ТТН); с ТТН — номер и ссылка отслеживания | `shipped` |
| `ttn` | ТТН введена/изменена, когда заказ уже в доставке (номер ещё не был в письме) | `ttn:<номер>` |
| `arrived` | опрос НП: статус 7/8 «прибув у відділення» | `arrived:<номер>` |
| `paid` | менеджер поставил «Оплачено» | `paid` |
| `canceled` | заказ отменён (менеджером или покупателем) | `canceled` |

Письмо ставится в очередь после коммита (`schedule` → Celery; без Redis — сразу). Журнал `CustomerNotification`
(статус, ошибка SMTP) — в карточке заказа кабинета, там же «Надіслати ще раз»; в Django admin — только просмотр.
Выключатель — «Надсилати покупцям листи про замовлення» в настройках магазина (`SiteSettings.notify_customers`).

### warehouse
Модели:
- `Warehouse` (склад продавца), `Supplier` (общий справочник поставщиков);
- `StockMovement` — **журнал движений, единственный источник истины**. Типы: `in`, `out`, `return_in`,
  `return_out`, `adjustment` (излишек), `adjustment_out` (недостача), `transfer_in`, `transfer_out`.
  Количество всегда > 0 (ограничение в БД), направление задаёт тип. Записи не редактируются и не удаляются
  (API — только чтение и создание через сервис, admin — только чтение, FK с `PROTECT`);
- `StockBalance` — остаток пары (вариант, склад), кэш журнала;
- `InventoryDocument` — загруженная накладная + распознанные данные + отчёт проведения
  (`extracted_data.processing_report`);
- `ProductBarcode`, `VariantMatchMemory`, `CurrencyRate`.

**Остатки** (`ProductVariant`): `stock` — физический остаток по всем складам, `reserved` — резерв под заказы,
`available_stock = stock − reserved`. Все — `Decimal(12,3)` (метры, кг).

**Сервис `warehouse/stock.py`** — единственное место, меняющее остатки:

| Функция | Что делает |
|---|---|
| `receive` | приход от поставщика (`in`, поставщик обязателен) или возврат клиента (`return_in`) |
| `write_off` / `return_to_supplier` | ручной расход / возврат поставщику; не трогает зарезервированное |
| `transfer` | перемещение между складами (`transfer_out` + `transfer_in`) |
| `adjust` | инвентаризация: приводит склад к факту движением излишка/недостачи |
| `reserve` / `release` | резерв под заказ (всё или ничего) / снятие резерва |
| `write_off_reserved` | списание зарезервированного при выдаче заказа (сначала склад по умолчанию) |
| `rebuild_from_journal` | пересчёт кэшей по журналу (admin-действие «Сверить и пересчитать») |
| `reverse_receipts` | сторно приходов (`in_reversal`): всё или ничего, проданное и зарезервированное не трогает |

Как защищено от гонок: каждая функция — `transaction.atomic()`, строки блокируются `select_for_update`
в фиксированном порядке (варианты по id → остатки по id склада), поэтому нет ни оверселла, ни deadlock'ов.
Нехватка товара → `InsufficientStockError` → API отвечает `400 {"detail", "code": "insufficient_stock", ...}`
(обработчик `app/core/exceptions.py`).

**Приёмка накладной** (`services.py`) — три шага:
1. **Загрузка** (`POST inventory-documents/`): проверка расширения/размера, SHA-256 (тот же файл второй раз не
   загрузить), файл кладётся в приватное хранилище, сразу выполняется разбор. Каждая строка получает статус:
   `matched` (память сопоставлений / штрихкод / артикул), `needs_review` (найден только похожий по названию —
   fuzzy ≥ 80 %), `new` (будет создан скрытый товар), `invalid` (нет названия/количества/цены).
2. **Проверка**: `POST inventory-documents/{id}/lines/{n}/` с `{"variant": id}` или `{"create_new": true}`;
   подбор товара — `GET inventory-documents/variant-search/?q=…`.
3. **Проведение** (`POST …/process/`): запрещено, пока есть `needs_review` (или `accept_suggestions=true`) и если
   накладная с тем же номером этого поставщика уже проведена (или `allow_duplicate_number=true`). Одинаковые новые
   позиции в одной накладной создают один товар. Подтверждённые сопоставления запоминаются для поставщика —
   следующая накладная сопоставится автоматически. Отчёт: `{received, created, skipped}`.

Поставщик определяется по шапке накладной, если у `Supplier.code` указан код парсера (`aquadom`, `presto`, `santan`).

**Эндпоинты** (`/api/warehouse/`, доступ — суперпользователь или одобренный активный продавец, только свои склады):

| Метод и путь | Назначение |
|---|---|
| `GET/POST/PATCH warehouses/`, `GET warehouses/{id}/balances/` | склады и остатки |
| `GET/POST/... suppliers/` | поставщики (удаление = деактивация) |
| `GET stock-movements/`, `GET stock-movements/{id}/` | журнал (фильтры: тип, склад, вариант, документ) |
| `POST stock-movements/` | ручная операция `in/out/return_in/return_out` |
| `POST stock-movements/transfer/` · `return_supplier/` · `inventory/` | перемещение, возврат, инвентаризация |
| `GET/POST inventory-documents/` | накладные (xlsx/xls/xml/yml, ≤10 МБ) |
| `POST inventory-documents/{id}/parse/` | разобрать файл заново (например, после выбора поставщика) |
| `POST inventory-documents/{id}/lines/{n}/` | сопоставить строку: `{"variant": id}` / `{"create_new": true}` |
| `GET inventory-documents/variant-search/?q=` | подбор товара для строки |
| `POST inventory-documents/{id}/process/` | провести накладную → отчёт `{received, created, skipped}` |
| `GET inventory-documents/{id}/file/` | скачать исходный файл (накладные не раздаются через `/media/`) |
| `POST inventory-documents/{id}/scan/` | пик сканера = +1 шт. по документу |
| `GET inventory-documents/{id}/print/` | PDF (генерируется в памяти, не сохраняется в media) |
| `POST stock-movements/find_by_barcode_or_sku/` | сканер: поиск по штрихкоду/артикулу |
| `POST stock-movements/create_and_add/` | сканер: новый товар (+ приход, если указан документ) |
| `GET scanner-test/` | тестовая страница сканера (только staff) |

### products — редактор кабинета (`/api/manage/…`, `products/manage.py`)
Администратор редактирует все товары, продавец — только свои. `manage/products/` — список с поиском (название,
артикул, штрихкод; без JOIN, чтобы не искажать суммы), фильтрами (категория, показ, без фото, есть на складе),
сортировкой и сводкой (вариантов, мин. цена, остаток, виден ли); создание с первым вариантом; правка; `variants/`,
`photos/` (первое — главное, остальные — галерея; `photos/<id>/main|delete`; файлы с диска не удаляются — в старых
данных один файл бывает у нескольких записей); `bulk/` (показать / скрыть / категория). `manage/variants/<id>/` —
правка/удаление варианта. Товар или вариант с заказами или движениями склада удалить нельзя — только скрыть.
Цена со «старой ценой» → скидка: `products.services.discount_fields` (общая с импортом). Остатки — только чтение.

**Этикетки** (`/api/warehouse/labels/?variants=…|products=…&size=thermal|a4&copies=N`, `warehouse/labels.py`):
термопринтер 58×40 мм или лист A4 3×8 (70×37 мм); название, цена, артикул, магазин; EAN-13 при верной контрольной
цифре, иначе Code128 с тихими зонами.

### imports — импорт товаров
- `ImportSource` — источник товаров продавца: `feed` (YML/XML/CSV/Excel/JSON по ссылке или файлом), `api`
  (JSON, страницы, путь к списку), `web` (кабинет поставщика с логином через адаптер). Доступ: без авторизации,
  Basic, Bearer, ключ в заголовке/ссылке, вход на сайт. Пароль/токен хранится **зашифрованным** (`app.core.crypto`,
  ключ `CREDENTIALS_KEY` или производный от `SECRET_KEY`) и в API не возвращается.
- `SupplierItem` — товар в каталоге поставщика (промежуточная таблица): цена, закупка, валюта, остаток и наличие
  у поставщика, фото, характеристики; статус `new` / `linked` (связан с нашим вариантом) / `ignored`; `missing` —
  пропал из последней выгрузки.
- `ImportRun` — запуск: загрузка шаблона (с предпросмотром строк) или синхронизация источника; статистика, ошибка.
- **Синхронизация** (`services.sync_source`, Celery): скачать → разобрать → обновить позиции → связать новые с нашими
  вариантами по штрихкоду, затем артикулу → обновить цену/закупку связанных (режим «РРЦ поставщика» или «закупка +
  наценка», курс из `CurrencyRate`, округление), при включённой опции скрыть товар, если у поставщика нет, а у нас
  пусто (и вернуть, когда появится; скрытые вручную не трогаются). Меняются **только товары этого продавца**
  (администратор — ещё и общие товары без продавца). **Склад не меняется**: остатки поставщика — информация.
- **Шаблон** (`template.py`): строка ищет товар по артикулу, затем по штрихкоду → обновляет (пустая ячейка = «не
  менять») или создаёт (новые скрыты, если не выбрано «показывать»); «Код групи» объединяет строки в варианты одного
  товара; категории и бренды создаются по названию; колонка «Залишок» проводится **инвентаризацией** на выбранный
  склад (повторная загрузка того же файла остатки не удваивает). Применение — в фоне, фото — отдельной задачей.
- Разбор файлов: колонки и теги распознаются по синонимам (укр./рус./англ., «Ціна, грн», «Опт. ціна»…), строка
  заголовков ищется среди первых 30; для нестандартных — `field_map` (колонка, тег, `@атрибут`, путь `a.b` в JSON).
- Загрузка по ссылкам — `app.core.http.fetch`: только http(s) и публичные IP (не localhost, не сеть docker, не
  metadata облака), каждый редирект проверяется, авторизация не уходит на другой хост, лимит 50 МБ (фото — 10 МБ).

| Метод и путь (`/api/imports/`) | Назначение |
|---|---|
| `GET template/?type=xlsx\|csv[&products=1]` | шаблон (пустой или с товарами продавца) |
| `GET/POST runs/`, `GET runs/{id}/`, `DELETE runs/{id}/` | загрузка шаблона → предпросмотр; отмена неприменённой |
| `GET runs/{id}/rows/?filter=errors\|create\|update\|warnings` | строки предпросмотра с ошибками и предупреждениями |
| `POST runs/{id}/apply/` | применить (`warehouse`, `publish`) — в фоне |
| `GET/POST/PATCH/DELETE sources/` | источники поставщиков (`secret` — только запись) |
| `POST sources/{id}/sync/` | синхронизировать сейчас (в фоне) |
| `GET sources/{id}/items/?status=&q=&category=&missing=&available=` | позиции поставщика (+ `our_price` по правилам источника) |
| `GET sources/{id}/categories/`, `GET sources/{id}/runs/` | категории поставщика, история синхронизаций |
| `POST sources/{id}/link/` · `items-status/` · `publish/` | связать с нашим товаром · пропустить/вернуть · создать товары |
| `GET adapters/` | адаптеры сайтов поставщиков и их настройки |

### callback

## 5. Парсеры накладных (`app/parsers`)

```
load_rows(file)               core/loader.py   xlsx/xls/xml/yml/pdf → строки; фото/скан → NeedsAI
pipeline.parse_rows(rows)     pipeline.py      что использует склад:
  1. колонки, заданные оператором для этой накладной → engine "manual"
  2. registry.parse(rows)     detect + suppliers/*.py (aquadom, presto, santan, default) → engine "parser"
  3. quality.assess()         кол-во × цена = сумма в строках, сумма строк = итог (± ПДВ)
     сошлось → результат парсера без изменений
  4. не сошлось → кандидаты: профили колонок поставщика ("profile"), разбор по содержимому
     universal.py ("universal"), готовый ИИ-разбор ("ai"); побеждает лучшая проверка
  → {meta, items[], totals, quality, engine, columns?, detected_supplier}
```
**Почему так.** Накладные составляют вручную и каждый раз по-разному: колонки переставлены, подписаны неверно или не
подписаны, латинская «i» вместо «і». Поэтому решает арифметика, а не заголовки. Хорошо разобранные файлы основным
парсером не меняются никогда (проверено эталоном).

**universal.py** — колонки по содержимому: тройка числовых колонок, где кол-во × цена = сумма; название — самый
длинный текст; «шт/м/кг» — единица; 8–14 цифр — штрихкод; короткие коды — артикул (номер позиции 1, 2, 3… — нет).
Ничьи решают подписи колонок; если есть цены без ПДВ и с ПДВ — берётся **с ПДВ** (фактически уплачено).

**ИИ (ai.py)** — Claude получает таблицу текстом (Excel) или сам файл (PDF/фото), отвечает строго по схеме (инструмент
`record_invoice`). Режимы `INVOICE_AI_MODE`: `off` (по умолчанию), `manual` (кнопка), `auto` (ещё и сам, если накладная
не разобралась). Модель — `INVOICE_AI_MODEL` (`claude-opus-5-5`; дешевле — `claude-sonnet-5-5`). Задача
`warehouse.parse_document_ai` (Celery), статус — `InventoryDocument.ai_status`.

**Защита от регрессий.** `cd app && python -m parsers.regress snapshot ПАПКА` — запомнить, как разбираются реальные
файлы; после изменений `compare ПАПКА` покажет OK / CHANGED (посмотреть глазами) / LOST (регрессия) / FIXED.
Реальные накладные хранить в `data/invoice-samples/` (папка `data/` не попадает в git). Обезличенные копии макетов —
`apps/warehouse/tests/parser_cases/*.json` (тест сверяет результат; обновить — `regress record`).

Проведение результата на склад: `warehouse/services.py::process_inventory_document`.

## 8. Запуск

**Production (Docker):**
```bash
cp .env.example .env            # заполнить SECRET_KEY, POSTGRES_*, DJANGO_ALLOWED_HOSTS, EMAIL_*, TOKEN_BOT…
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec app python app/manage.py createsuperuser   # is_admin + is_superuser
```
Сервисы: `db` (PostgreSQL 14, данные в `./data/db`), `redis`, `migrate` (одноразово: миграции + статика),
`app` (Django + gunicorn, healthcheck `/api/health/`), `worker` (Celery: импорт, синхронизация, фото, уведомления),
`beat` (расписание синхронизаций; один экземпляр), `frontend` (SSR-витрина, Node), `nginx` (порт
`HTTP_PORT`, по умолчанию 80: `/api`, `/admin`, `/account` → Django, остальное → витрина). Хосты БД/Redis задаёт
compose — в `.env` их менять не нужно. Обязательно задать `SESSION_SECRET` (`openssl rand -hex 32`);
без HTTPS — `INSECURE_COOKIES=true`, иначе браузер не вернёт cookie сессии.
TLS: терминировать перед `web` (Cloudflare / certbot / балансировщик), в `.env` — `TRUSTED_PROXY=True`.

**Существующая БД** (`./data/db` с прошлых версий) — перед первым запуском сделать бэкап и пометить миграцию:
```bash
docker compose -f docker-compose.prod.yml run --rm migrate python app/manage.py migrate products 0014 --fake
```

**Обновление на сервере** (новая версия кода; особенно — переход на Django 5.2, там новые миграции allauth):
```bash
git pull
# 1. бэкап БД (обязательно)
docker compose -f docker-compose.prod.yml exec db sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > backup-$(date +%F).dump
# 2. только для перехода на Django 5.2: обе проверки должны вернуть 0 строк
docker compose -f docker-compose.prod.yml exec db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB" -c "
  SELECT lower(email), count(*) FROM account_emailaddress WHERE verified GROUP BY lower(email) HAVING count(*) > 1;"'
docker compose -f docker-compose.prod.yml exec db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB" -c "
  SELECT user_id, count(*) FROM account_emailaddress WHERE \"primary\" GROUP BY user_id HAVING count(*) > 1;"'
# 3. сборка и запуск (сервис migrate применит миграции сам)
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml logs migrate | tail -20
```
Первая проверка нашла строки — один и тот же email подтверждён дважды (например, `Ivan@…` и `ivan@…`): лишнюю
запись удалить в Django admin («Email addresses») **до** обновления, иначе миграция allauth упадёт. Вторая —
не страшно, allauth исправит сам (миграция `0008…fixup`), но лучше знать заранее.
**Откат:** `git checkout <прошлый коммит>`, `docker compose -f docker-compose.prod.yml down`, восстановить БД
`docker compose -f docker-compose.prod.yml up -d db` → `docker compose -f docker-compose.prod.yml exec -T db sh -c
'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backup-….dump` → `up -d --build`.
После обновления: вход в магазин и в `/admin/`, «Забули пароль?», кабинет продавца.

**Демо-данные** (проверить корзину и оформление, когда у товаров нет остатков) — только на тестовой базе:
```bash
docker compose -f docker-compose.prod.yml exec app python app/manage.py seed_demo --force   # Docker
python app/manage.py seed_demo                                                               # локально, DEBUG=True
```
Каждому видимому варианту без остатка (до `--limit 100`, новые первыми) — приход `--qty 20` шт. от
«Демо-постачальника» (документ `DEMO`) на склад по умолчанию продавца; пустой каталог — сначала 10 демо-вариантов
(4 категории). Повторный запуск ничего не задваивает. Приходы — обычные записи журнала склада, их не удалить
(только списать), поэтому при `DEBUG=False` команда без `--force` не запускается.

**Ветки и PR.** `main` — то, что выкатывается на сервер; `develop` — общая ветка разработки. Новая задача —
ветка от `develop` (`feature/…`, `fix/…`), PR в `develop`; релиз — PR `develop` → `main`.

**Локальная разработка:** `docker compose -f docker-compose.dev.yml up -d` (БД и Redis), в `.env`:
`DEBUG=True`, `POSTGRES_HOST=localhost`, `REDIS_URL=redis://localhost:6379/1`; затем
`python app/manage.py migrate && python app/manage.py runserver`; витрина — `cd frontend/web && npm install &&
npm run dev` (http://localhost:3000, ходит в Django на :8000). Фоновые задачи: `celery -A config worker -B -l info`
или `CELERY_TASK_ALWAYS_EAGER=True` (задачи выполняются сразу в запросе). Переключать «dev/боевой» правкой кода не нужно —
всё задаётся переменными окружения.

### 2026-10-25 — Накладные: та же поставка не приходуется дважды, отмена проведения (ветка `feature/invoice-duplicates`)
**Дубли.** Раньше ловились только тот же файл (SHA-256) и тот же номер у того же поставщика. Пересохранённый файл,
фото вместо Excel, «определить автоматически» вместо выбора поставщика или номер «№ 0077» вместо «77» проходили.
Теперь `warehouse/duplicates.py` сравнивает данные (у накладной хранятся `number_key`, `fingerprint`, `lines_total`;
для старых — заполняет миграция `0018`):

| Признак | Условие | Окно |
|---|---|---|
| номер | «№ 00123» = «123», «ВН-0045» = «BH 45»; поставщик тот же или у одной не указан | 365 дней |
| строки | тот же набор «название + количество + цена» (номер мог не распознаться) | 120 дней |
| похожие | та же сумма строк и ≥ 80 % одинаковых строк (от трёх строк) | 120 дней |

Карточка непроведённой накладной показывает совпадения (`duplicates` в API): «вже проведена» — проведение
запрещено, пока оператор не отметит «Я перевірив: це інша поставка» (`allow_duplicate`; в отчёте — кто подтвердил);
«ще не проведена» — подсказка. Одинаковые поставки бывают каждый месяц, поэтому совпадение — не вечный запрет.
Проведение и отмена блокируют строку продавца: две копии, проводимые одновременно, — одна проходит, вторая видит дубль.

**Сканер + проведение (была реальная дыра).** В режиме «Приймання» сканер сразу приходует +1 по накладной; после
«Провести» товар приходовался второй раз всеми строками. Теперь проведение вычитает уже принятое по документу
(`already_received` в отчёте), а отсканированное сверх накладной показывает отдельно (`scanner_extra`).

**Отмена проведения (сторно).** `POST …/inventory-documents/{id}/reverse/ {reason}` — движения нового типа
«Сторно прихода» (`in_reversal`, расходный) на всё, что документ оприходовал. Журнал не правится. Проданное или
зарезервированное отменить нельзя — ответ перечисляет, чего не хватает, ничего не меняется. После отмены документ
снова черновик (история отмен — `extracted_data.reversals`), его можно исправить и провести.

**Проверено вживую** (временная БД, кабинет): накладная проведена → копия с «№ 77» без поставщика: «Схоже, цю
поставку вже завантажували… ті самі рядки, той самий номер», без галочки не проводится (сообщение по-украински и
по-русски), с галочкой — проведена с пометкой «підтвердив …», отмена → остатки как после одного прихода, в журнале
«Прихід» и «Сторно приходу», в списке «Проведення скасовано». Тесты: backend 250 (+12), frontend 32.
